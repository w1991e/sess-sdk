# Release packet: `@sess.si/mcp@0.1.1`

Maintainer document; not packed. Preparing this release publishes nothing. The tag, the
`npm-mcp-release` environment approval and the npm 2FA stage approval are the owner's actions.

The registry has `0.1.0` on `latest` and `0.1.0-rc.4` on `next`. `0.1.1` is stable: the release guard
derives dist-tag `latest` for it. `next` stays at `0.1.0-rc.4`.

## What 0.1.1 contains

- The `0.1.1` entry in [CHANGELOG.md](../CHANGELOG.md): `sess_response` re-wait, routing lines in the
  tool descriptions, `annotations.title` on every tool, the `sess_complete` description.
- `mcpName` is `si.sess/sess`, so the MCP Registry can list this package. `destructiveHint` stays
  `true` on `sess_complete`.
- The package description is the signed one-liner. `server.json` adds the npm package and the
  repository field.
- The runtime SDK dependency, exact: `@sess.si/sdk@0.1.1`, from the registry.
- The tool schema stays `sess-mcp-tools/4`.

## Maintainer steps

1. Confirm the reviewed PR carrying this packet is merged and its CI is green on master. Note the
   merged master commit `<sha>` and check that it is version `0.1.1`:
   `git show <sha>:adapters/mcp/package.json | grep '"version"'`.
2. Tag that exact commit and push the tag:

   ```sh
   git tag mcp-v0.1.1 <sha>
   git push origin mcp-v0.1.1
   ```

3. The workflow **Publish approved MCP adapter release** (`.github/workflows/mcp-release.yml`)
   starts. Its prepare job runs the release guards, `npm run check` and `npm audit` at the tag,
   uploads the tested tarball and prints its SHA-256 in the run summary. That SHA-256 must equal
   the value above, and the derived dist-tag must be `latest`.
4. Approve the `npm-mcp-release` environment for the publish job. It stages exactly the tested
   tarball with provenance on dist-tag `latest` (`npm stage publish`; nothing is installable yet).
5. Check and approve the stage with npm 2FA:

   ```sh
   npm stage list @sess.si/mcp --json
   npm stage download <stage-id>
   shasum -a 256 sess.si-mcp-0.1.1-<stage-id>.tgz   # must equal the SHA-256 above
   npm stage view <stage-id>                        # tag must be latest
   npm stage approve <stage-id>                     # npm 2FA
   ```

6. The readback job waits up to 60 minutes for the approval, then checks version, repository and
   directory, registry integrity, dist-tag, dependencies and provenance. If it timed out, re-run
   the failed jobs after approving.
7. Read back yourself:

   ```sh
   npm view @sess.si/mcp@0.1.1 version dependencies dist.integrity dist.attestations --json
   npm view @sess.si/mcp dist-tags --json     # latest: 0.1.1; next stays 0.1.0-rc.4
   ```

   `dist.integrity` must equal the integrity above, `dependencies` must name
   `"@sess.si/sdk": "0.1.1"`, and `dist.attestations.provenance` must be present.

## After publication, in this order

1. The owner submits `server.json` to the MCP Registry with `mcp-publisher` ([LISTINGS.md](../LISTINGS.md)).
   It takes the one-liner, the npm package and the repository field at the publish.
2. A reviewed PR records the published version, integrity, dist-tag and provenance in
   `compatibility.json` (0.1.0 moves to `earlier`), sets `listing.json` `stdio.status` to `published`
   and `providers.mcpRegistry.npmPackage.publishedVersion` and `publishedMcpName` to what the registry
   serves, and regenerates the listing artifacts.
3. The w1991e/sess pin PR moves `apps/api` and `apps/runtime` to `@sess.si/mcp@0.1.1`.
4. The next window, preview first; readback; the requalification round on production, cases 1 to 5
   plus the two negative cases, on claude.ai and Cursor, which also records Cursor's real registration
   body and its size, with redirect addresses generalised and no secret.
