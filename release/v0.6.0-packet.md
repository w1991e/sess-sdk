## What SDK 0.6.0 contains

The `0.6.0` entry in [`CHANGELOG.md`](../CHANGELOG.md):

- `sessions.listEvents()` returns the closing receipt as `closing`, beside `events`, never as an Event, and only once the Session has ended with at least one accepted answer. New type `SessionClosing`.
- `receipts.verifyClosing({ sessionId, closing })` verifies it against the Session's Event log and the published keys; `verifyClosingReceipt` in `@sess.si/sdk/receipts` verifies one offline.
- Unchanged: `verifyDecisionReceipt` still refuses a closing receipt as newer (`RECEIPT_NEWER`), and `verifyWebhook` still refuses every Session message but `response.accepted`.
- The contract is Sess's OpenAPI at master `938852ba` ([`contract/contract-lock.json`](../contract/contract-lock.json); the same file as at `79caadd8`): `SessionClosing` beside the Event log, the tighter limits, and the types of `POST /v1/receipts/verify-closing` (no method: the SDK verifies the closing receipt itself with `receipts.verifyClosing()`). The closing-receipt-v1 specification and conformance corpus are copies from Sess `7be0bf3a` ([`docs/spec/source.json`](../docs/spec/source.json)).
- The runtime dependencies are unchanged: `canonicalize` 5.1.0, `jose` 6.2.12, `standardwebhooks` 1.1.1.
- `SDK_VERSION` is `0.6.0`. The README's first code block is unchanged at twelve lines.

## The owner's sitting, in order

Each step names what a good result looks like. A step that does not look like that stops the sitting; nothing after it runs.

1. Confirm `npm view @sess.si/sdk dist-tags --json` shows `latest: 0.5.0` and `next: 0.1.0-rc.10`.
2. Tag the squash commit on master that merged this packet's PR (check it with `git show <sha>:release/sdk-next-candidate.json`; its version is `0.6.0`):

   ```sh
   git tag v0.6.0 <sha>
   git push origin v0.6.0
   ```

3. **Publish approved SDK release** (`.github/workflows/release.yml`) runs `npm run check` at the tag, uploads the tested tarball and prints its SHA-256. Good: it equals the value above, and the dist-tag it derives is `latest`.
4. Approve the `npm-release` environment. Good: the job stages exactly the tested tarball, with provenance, on `latest`.
5. Check the stage, then approve it with npm 2FA:

   ```sh
   npm stage list @sess.si/sdk --json
   npm stage download <stage-id>
   shasum -a 256 sess.si-sdk-0.6.0-<stage-id>.tgz   # must equal the SHA-256 above
   npm stage view <stage-id>                         # tag must be latest
   npm stage approve <stage-id>                      # npm 2FA
   ```

6. The readback job checks integrity, the dist-tag and provenance. Then:

   ```sh
   npm view @sess.si/sdk@0.6.0 version license dist.integrity --json
   npm view @sess.si/sdk dist-tags --json            # latest: 0.6.0; next: 0.1.0-rc.10
   ```

   Good: version `0.6.0`, the integrity above, `latest` = `0.6.0`.

7. **The registry transition** (not the owner's keyboard): one reviewed PR on master, ASTRA at its final head. It contains `npm run pin:update`; in `adapters/mcp`, `npm run sdk:switch-to-registry -- --apply`; `adapters/openclaw/compatibility.json` `sdk.evidence` from step 3's run; the compatibility page line (text 1); the MCP CHANGELOG's dependency line on `@sess.si/sdk` 0.6.0; and the packet of `@sess.si/mcp` 0.6.0 with its expected tarball, which can only be computed once the SDK it depends on is on the registry. `pin:update` also moves the OpenClaw adapter's and the create-agent template's SDK pins to 0.6.0 in the repository; neither package is released with this SDK (below).
8. **Owner:** `mcp-v0.6.0`, by its own packet's steps, the same shape as steps 2 to 6: tag, approve the environment, check the stage's SHA-256, approve with 2FA, read back. Good: the readback shows `@sess.si/mcp` `0.6.0` on `latest`, depending exactly on `@sess.si/sdk` `0.6.0`.

**`@sess.si/mcp` 0.6.0 must never ship on sdk 0.5.0.** It carries no new tool-description wording (Sess L-124 is not drafted or signed); its tool schemas stay `sess-mcp-tools/6`.
