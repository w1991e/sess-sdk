# Release packet: @sess.si/sdk 0.3.0 on `latest`

This is a maintainer document and is not packed. Preparing it publishes nothing. The tag, the protected-environment approval and the npm 2FA stage approval are owner actions.

Goal: the SDK verifies receipt v2 (`sess-receipt-2+jwt`, which commits by hash to the round's revision envelope) and bundle-v2, and still verifies receipt v1 and bundle-v1 exactly as before. This is a minor version. `latest` moves from `0.2.0` to `0.3.0` through the release workflow only; `next` stays at `0.1.0-rc.10`.

And 10:20Z: "The v2-capable releases are @sess.si/sdk 0.3.0, @sess.si/mcp 0.3.0 and @sess.si/openclaw 0.2.0: minor versions, v1 receipts still verified. ## What SDK 0.3.0 contains

The `0.3.0` entry in [`CHANGELOG.md`](../CHANGELOG.md):

- **Receipt v2:** `verifyDecisionReceipt` (with `revisionEnvelope` on its input) and `receipts.verifyResponse()` (with the response's own `revision_envelope`) verify `sess-receipt-2+jwt`. A missing, malformed or different envelope is refused with `REVISION_ENVELOPE_MISMATCH`, after the issuer, audience, expiry and signature checks. Receipt v1 is unchanged.
- **Types:** `revision_envelope` on `AcceptedResponse`, `SessionEvent` and the `response.accepted` webhook message, plus the new type-only exports `RevisionEnvelope`, `ReceiptClaimsV1`, `ReceiptClaimsV2`, `DecisionBundleV1` and `DecisionBundleV2`.
- **Bundles:** `verifyDecisionBundle` and `sess verify` read bundle-v2, with the new reason `revision`. A version above 2 is `unsupported_version`.
- **The User-Agent:** `SDK_VERSION` is `0.3.0`.

The runtime dependencies are unchanged: `canonicalize` 5.1.0, `jose` 6.2.12, `standardwebhooks` 1.1.1. The `revision_envelope` types are written by hand; the contract snapshot is unchanged.

**Receipt v2 on Sess:** no Sess deployment issues receipt v2 yet. The issuing side (Sess #1138) deploys in the next window, after this release and the mcp and openclaw releases. Until then this SDK keeps verifying the v1 receipts Sess issues today. The receipt-v2 and bundle-v2 specifications and the bundle-v2 corpus are copies from Sess commit `c67c792` (#1138's head when prepared). If #1138 changes them before it merges, they are refreshed in a later SDK release.

## How it reaches master

## Maintainer steps

1. Confirm `npm view @sess.si/sdk dist-tags --json` shows `latest: 0.2.0` and `next: 0.1.0-rc.10`.
2. Tag the squash commit on master that merged #57 (check it with `git show <sha>:release/sdk-next-candidate.json`):

   ```sh
   git tag v0.3.0 <sha>
   git push origin v0.3.0
   ```

3. **Publish approved SDK release** (`.github/workflows/release.yml`) runs `npm run check` at the tag, uploads the tested tarball and prints its SHA-256, which must equal the value above. For a stable version it derives the dist-tag `latest`.
4. Approve the `npm-release` environment. The job stages exactly the tested tarball, with provenance, on `latest`.
5. Check the stage, then approve it with npm 2FA:

   ```sh
   npm stage list @sess.si/sdk --json
   npm stage download <stage-id>
   shasum -a 256 sess.si-sdk-0.3.0-<stage-id>.tgz   # must equal the SHA-256 above
   npm stage view <stage-id>                         # tag must be latest
   npm stage approve <stage-id>                      # npm 2FA
   ```

6. The readback job checks integrity, the dist-tag and provenance. Then:

   ```sh
   npm view @sess.si/sdk@0.3.0 version license dist.integrity --json
   npm view @sess.si/sdk dist-tags --json            # latest: 0.3.0
   ```

7. **Registry transition, with the adapter releases' prep,** in one reviewed PR on master after step 6. Consumers move from `0.2.0` to `0.3.0`, and the prepared record is removed.
   - `npm run pin:update`.
   - In `adapters/mcp`: `npm run sdk:switch-to-registry -- --apply`.
   - By hand: `adapters/openclaw/compatibility.json` `sdk.evidence` names 0.3.0 and its release run.
   - The references `pin:update` does not touch, as for 0.2.0.
   - `@sess.si/mcp` 0.3.0 and `@sess.si/openclaw` 0.2.0: versions, CHANGELOGs, compatibility records, listings and their packets, with adapter tests that verify a receipt v2 through the real SDK. Each is then tagged and staged on the owner's keyboard, mcp first.

## Not in this packet

`@sess.si/mcp` 0.3.0 and `@sess.si/openclaw` 0.2.0 install the SDK from the registry, and `check:pin` refuses a consumer that names an unpublished SDK. Their version moves therefore follow this release, in step 7's PR. Neither needs a code change for receipt v2: both pass the response to `client.receipts.verifyResponse`. `@sess.si/create-agent` keeps its version.
