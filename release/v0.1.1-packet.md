# Release packet: @sess.si/sdk 0.1.1 on `latest`

This is a maintainer document and is not packed. Preparing it publishes nothing. The tag, the protected-environment approval and the npm 2FA stage approval are owner actions.

Goal: the npm package page for `@sess.si/sdk` gains `keywords` and a `homepage` at the docs quickstart, with no API change. `latest` moves from `0.1.0` to `0.1.1` through the release workflow only. `next` stays at `0.1.0-rc.10`.

## What SDK 0.1.1 contains

The `0.1.1` entry in [`CHANGELOG.md`](../CHANGELOG.md):

- `keywords`: mcp, agent, human-in-the-loop, approval, form, receipt, claude, openai.
- `homepage`: https://docs.sess.si/quickstart/ (was the repository README).
- README: the install and verify commands name `0.1.1`; the release status line. These are proposed for the owner's line-by-line sign-off below.
- `SDK_VERSION` is `0.1.1`, so the default `User-Agent` names the new version. No other source change.

Runtime dependencies are unchanged: `canonicalize` 5.1.0, `jose` 6.2.12, `standardwebhooks` 1.1.1.

## README lines for the owner's sign-off

The README is packed: it becomes the npm page for `latest` and cannot change for 0.1.1 after publication.

- Install: `npm install --save-exact @sess.si/sdk@0.1.1`.
- Release status: "`0.1.1` is the current release, served under the `latest` dist-tag. Its API is that of `0.1.0`, the first stable release. `next` stays at the last release candidate, `0.1.0-rc.10`. The changelog describes each version; `npm view @sess.si/sdk dist-tags` shows what the registry serves now."
- Verify: `npx -p @sess.si/sdk@0.1.1 sess verify …`, and "The `sess` command first ships in `0.1.0-rc.5`; any later version, `0.1.1` included, has it."

## Maintainer steps

1. Confirm `npm view @sess.si/sdk dist-tags --json` shows `latest: 0.1.0` and `next: 0.1.0-rc.10`.
2. Tag this packet's merge commit (check it with `git show <sha>:release/sdk-next-candidate.json`):

   ```sh
   git tag v0.1.1 <sha>
   git push origin v0.1.1
   ```

3. **Publish approved SDK release** (`.github/workflows/release.yml`) runs `npm run check` at the tag, uploads the tested tarball and prints its SHA-256, which must equal the value above. For a stable version it derives the dist-tag `latest`.
4. Approve the `npm-release` environment. The job stages exactly the tested tarball, with provenance, on `latest`.
5. Check the stage, then approve it with npm 2FA:

   ```sh
   npm stage list @sess.si/sdk --json
   npm stage download <stage-id>
   shasum -a 256 sess.si-sdk-0.1.1-<stage-id>.tgz   # must equal the SHA-256 above
   npm stage view <stage-id>                         # tag must be latest
   npm stage approve <stage-id>                      # npm 2FA
   ```

6. The readback job checks integrity, the dist-tag and provenance. Then:

   ```sh
   npm view @sess.si/sdk@0.1.1 version license keywords homepage dist.integrity --json
   npm view @sess.si/sdk dist-tags --json            # latest: 0.1.1
   ```

7. **Registry transition:** `npm run pin:update` on master, in its own reviewed PR. Consumers move from `0.1.0` to `0.1.1`; the prepared record is removed.

## Not in this packet
