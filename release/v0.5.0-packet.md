## What SDK 0.5.0 contains

The `0.5.0` entry in [`CHANGELOG.md`](../CHANGELOG.md): Sess's tighter text limits in the SDK's own checks, so an over-long text is refused before the request, with the message that names the limit.

- The limits come from Sess's OpenAPI at Sess `spec/surface-limits-signed` `9f8e199b` (the contract commit on this branch), one source with Sess's drift test.
- Verifying receipts is unchanged. A receipt issued under the old limits verifies forever: the four protected bounds and their tests stay (the receipt verifier's action label, 24; the shared receipt title, 60; the "Your name" answer, 80; and the limits used to read stored revisions).
- The runtime dependencies are unchanged: `canonicalize` 5.1.0, `jose` 6.2.12, `standardwebhooks` 1.1.1.
- `SDK_VERSION` is `0.5.0`.

## The owner's sitting, in order

Each step names what a good result looks like. A step that does not look like that stops the sitting; nothing after it runs.

1. Confirm `npm view @sess.si/sdk dist-tags --json` shows `latest: 0.4.0` and `next: 0.1.0-rc.10`.
2. Tag the squash commit on master that merged this packet's PR (check it with `git show <sha>:release/sdk-next-candidate.json`; its version is `0.5.0`):

   ```sh
   git tag v0.5.0 <sha>
   git push origin v0.5.0
   ```

3. **Publish approved SDK release** (`.github/workflows/release.yml`) runs `npm run check` at the tag, uploads the tested tarball and prints its SHA-256. Good: it equals the value above, and the dist-tag it derives is `latest`.
4. Approve the `npm-release` environment. Good: the job stages exactly the tested tarball, with provenance, on `latest`.
5. Check the stage, then approve it with npm 2FA:

   ```sh
   npm stage list @sess.si/sdk --json
   npm stage download <stage-id>
   shasum -a 256 sess.si-sdk-0.5.0-<stage-id>.tgz   # must equal the SHA-256 above
   npm stage view <stage-id>                         # tag must be latest
   npm stage approve <stage-id>                      # npm 2FA
   ```

6. The readback job checks integrity, the dist-tag and provenance. Then:

   ```sh
   npm view @sess.si/sdk@0.5.0 version license dist.integrity --json
   npm view @sess.si/sdk dist-tags --json            # latest: 0.5.0; next: 0.1.0-rc.10
   ```

   Good: version `0.5.0`, the integrity above, `latest` = `0.5.0`.

7. **The registry transition** (not the owner's keyboard): one reviewed PR on master, ASTRA at its final head. It contains `npm run pin:update`; in `adapters/mcp`, `npm run sdk:switch-to-registry -- --apply`; `adapters/openclaw/compatibility.json` `sdk.evidence` from step 3's run; the compatibility page line (text 1); and the packets of `@sess.si/mcp` 0.5.0, `@sess.si/openclaw` 0.3.0 and `@sess.si/create-agent` 0.3.0 with their expected tarballs. Those tarballs can only be computed once the SDK they depend on is on the registry, so their packets are written in this PR, as for 0.4.0.
8. **Owner:** `mcp-v0.5.0`, then `openclaw-v0.3.0`, then `create-agent-v0.3.0`, each by its own packet's steps. They follow the same shape as steps 2 to 6: tag, approve the environment, check the stage's SHA-256, approve with 2FA, read back. Good, for each: the readback shows the new version on `latest`, depending exactly on `@sess.si/sdk` `0.5.0`.
9. **The starter** (`w1991e/sess-agent-starter` `limits/plan-labels-way-1`): parity with create-agent 0.3.0 and the 0.5.0 pin, merged after step 8 (its CI checks parity against sess-sdk master and installs from the registry).
10. **Sess:** the pins car moves Sess to sdk 0.5.0 and mcp 0.5.0. The limits car (Sess `spec/surface-limits-signed`) then pins mcp 0.5.0 (ASTRA's F2), removes the drift exception and goes to ASTRA. Both go to production in the window that tightens the runtime, after the packages are published.
